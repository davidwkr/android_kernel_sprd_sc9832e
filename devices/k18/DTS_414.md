# K18 DTS for the 4.14 tree

Files in `arch/arm64/boot/dts/sprd/`: `sp9832e-1h10-k18.dts` and the new panel files
`lcd/lcd_st7801_oled206_mipi.dtsi`, `lcd/lcd_ch13613_oled206_mipi.dtsi`, `lcd/lcd_icna3311_oled214_mipi.dtsi`.
The K18 is a separate model. Ground truth is the decompiled stock DT of the unit (`devices/k18/stock.dts` and
`devices/k18/SPEC.md` of the 4.4 tree, read only). The board is the MT107 one, so the file is the MT107 DTS with the K18
stock values; layout and project decisions follow `devices/mt107/DTS_414.md`, `devices/dm63/DTS_414.md`,
`devices/dm63/PANEL_414.md`. Charger and gauge references: `devices/SC2721_CHARGER_MAP.md`, `devices/SC2721_FGU_MAP.md`.
Compile only (`devices/merge_watch_414.sh $B`, `make O=$B ... dtbs`): no dtc warning in the build; the decompiled dtb
shows the same warnings as `sp9832e-1h10-mt107.dtb` minus the one for the rotary node. Nothing was run on a watch.

Status: mapped = value from stock in a 4.14 binding the driver reads; disabled-TODO = left out, stock values named;
not needed = no 4.14 counterpart or no function.

## What is the same as the MT107

A normalised diff of the two stock DTs (phandle numbers ignored, `lcds` excluded) shows no difference in: root, memory,
chosen / bootargs, the 14 reserved-memory regions (no logo buffer), eMMC / SD, USB, regulators (same 14 `sprd,default-on`),
board NTC table, SIPC / WCN / modem / ion, gpio-keys (Volume Down ap-eic 2 code 0x43, Power PMIC EIC 1 code 0x74,
Function ap-eic 3 code 0x57, 50 ms) and the battery properties not listed below. The decompiled dtb reserved-memory
regions equal the stock ones address for address and size for size. The 4.14 handling of all of these is as in the
MT107 file.

Note 1. Which touch chip is fitted is not known and cannot be read from the unit, so both candidates with a 4.14 driver
stay enabled, as in stock and as on the MT107 (nothing is disabled the way the DM82 / DW100U DTS do). Checked against the
drivers for the K18 gpios (reset ap_gpio 145, irq 144, identical in the cst0xx and hynitron nodes): cst0xx probes first
(DT order), claims both gpios with `devm_gpiod_get_index` and resets the line. If it finds no chip it fails on the missing
ACK and the devm release frees the gpios, then hynitron claims them. If cst0xx binds, hynitron fails in `hyn_parse_dt`
(`devm_gpio_request_one`, -EBUSY) before the regulator, the reset pulse or any transfer. The stock hynitron `vdd_name`
is vddsdcore, as cst0xx, so no extra supply is touched.

## Display

Stock `lcds` has 23 nodes. Compared with the stock nodes of the DW100U (silver and v13m) and the MT107 with a script
(phandle lines ignored): CO5300 178, 1952, 204, 206 and 213 are byte-identical to the DW100U nodes (178, 1952, 204 and 206
also to the MT107 ones; the 213 node differs from the MT107 and the DM63 node). They reuse the DW100U dtsi
(`lcd_co5300_oled178`, `oled1952`, `oled204`, `oled206_dw100u`, `oled_213`); the MT107 213 dtsi is not used.

The three nodes new against the MT107, plus ICNA3311 148 (changed against the MT107), are converted with the 4.14 binding like the CO5300 work, because the generic panel
driver expresses them: command mode, 1 lane, rgb888, byte streams, vertical timings, identity brightness table.

| Stock node | 4.14 file | Size | DSI kbps | Init stream |
|---|---|---|---|---|
| lcd7801206 (ST7801, `lcd_st7801_oled206_mipi`) | `lcd_st7801_oled206_mipi.dtsi`, id 0x7801206 | 412 x 502 | 409000 | 8 commands: `11` (10 ms), `53 20`, `51 00`, `35 00`, `3a 77`, column 0..0x19b, row 0..0x1f5, `29` |
| lcd13613206 (CH13613, `lcd_ch13613_oled206_mipi`) | `lcd_ch13613_oled206_mipi.dtsi`, id 0x13613206 | 412 x 502 | 460000 | 10 commands: windows, `3a 77`, `35 00`, `53 5a`, `51 00`, `f0 51`, `ba 27 27 27`, `11`, `29` |
| lcd3311148 (ICNA3311, `lcd_icna3311_oled148_mipi`) | `lcd_icna3311_oled148_mipi.dtsi`, id 0x3311148 | 480 x 480 | 460000 | same 10 commands as 214 (stock streams, timings, sleep and brightness are identical to the 214 node); most likely fitted panel by touch geometry |
| lcd3311214 (ICNA3311, `lcd_icna3311_oled214_mipi`) | `lcd_icna3311_oled214_mipi.dtsi`, id 0x3311214 | 480 x 480 | 460000 | 10 commands: `fe 00`, `3a 77`, `35 00`, `53 20`, `51 00`, `63 ff`, windows 0..0x1df, `11`, `29` |

The stock `init-data` of the ST7801 and ICNA3311 nodes is stored as 32 bit cells; the cells were decoded to bytes and the
stream walks exactly. For all nine converted nodes a script compared the decompiled 4.14 dtb with the stock nodes: the
initial, sleep-in and sleep-out streams and the bit clock are byte identical, and every stock brightness table (256
commands `23 0a 00 02 51 NN`, NN = index) is the identity table, so the single brightness command `23 0a 00 02 51 00` of
the 4.14 oled-backlight is the same table. All eight use the stock power sequences (avdd gpio 33, reset gpio 50), default
brightness 120, esd check off, 68 x 121 mm (stock values, also for the 480 x 480 node), horizontal blanking 0 and a 128 MHz
DPI clock (same assumptions as `devices/dm63/PANEL_414.md`).

Panel controller confirmed from the unit's U-Boot log (`uboot_log`, 6 boots): `icna3311_mipi_init` and `icna3311_readid`
= `0x33 0x11` every time, so the panel is an ICNA3311. The log does not print the `lcd_id`; U-Boot has one ICNA3311 driver,
so it is the 148 or the 214 node, which carry identical commands and timings. Selection stays by the `lcd_id=ID<hex>` U-Boot
puts on the command line, as stock; `sprd,default-panel = "lcd_icna3311_oled148_mipi"` (480 x 480, matching the touch)
covers a command line without it.

Not converted (TODO, nothing invented): SH8601 x2 (8601204, 86011952), CH13613 x2 (13613, 13613213), ST7801 (7801), ST7797, GC9B71 x2, ST77916 x4, JD9855, dummy HD. AOD (stock `aod-in` / `aod-out`) has no 4.14
port. Stock `pwm-backlight` is unused by the OLED.

The charger caps every zone current to the adapter current (1050 mA, unknown adapter 1000 mA; both multiples of the 50 mA
step, all zone currents 700 / 900 / 800 mA are below it and above the 300 mA minimum) and every CV request to the battery
maximum, so the 4400 mV zone CV becomes 4395 mV, as the 4.4 `sprd_battery.c` does.

Representability of 4395 and 4400 mV in `sc2720_charger.c` (`sc2721_cv_model()`: programmed CV = 4200 + 100 * END_V mV +
(code - calibration) * 7.5 mV, code 6 bits with bit 0 cleared, END_V 0..2; the floor search `sc2721_cv_floor()` is only the
fallback when the model fails). Checked with a script that reproduces the model and the floor search for efuse calibration
0..63:

| Calibration | 4395 mV request (the one programmed: probe and zone CV) | 4400 mV request |
|---|---|---|
| default 0x20 (efuse valid flag clear) | END_V 1, code 0x2c: 4390 mV | same: 4390 mV |
| even 0..50 | END_V 1: 4390 mV | 4390 mV |
| odd 1..49 | END_V 1: 4397.5 mV (2.5 mV above the stock 4395 mV, the 4.4 rounding) | 4397.5 mV |
| odd 51..63 | END_V 2, code cal - 1: 4392.5 mV | 4392.5 mV |
| even 52..62 | END_V 2, code cal - 2: 4385 mV | END_V 2, code cal: 4400 mV |

The model succeeds for every calibration 0..63 for both voltages: the floor fallback is hit for none of them (it would
need `cv < 0` or `cv > 0x3f` after the model, which does not occur), so the probe cannot fail on 4395 mV and no calibration
logs the "not representable" warning. The 4400 mV zone request never reaches the model: it is capped to 4395 mV first, so
the even 52..62 case that would give 4400 mV (5 mV above the battery maximum) is not used. The efuse value of the unit is
not known.

Charge safety added on `kernel-4.14-charge-safety` (see `devices/SC2721_CHARGER_MAP.md` section 5, same as DM63):
hardware recharge enable with start/stop charge, `chg-ovi-gpios` / `chg-cv-gpios` as optional interrupts (OVP stops
charging and reports `POWER_SUPPLY_HEALTH_OVERVOLTAGE`; CV is diagnostic), and `cm-fullbatt-vchkdrop-volt` corrected
to the stock-derived 16 mV (`chg-end-vol-check` 4390 - `rechg-vol` 4374).

Not ported, so not protecting a charge on this kernel (as DM63 / MT107): hardware charge timer (covered in software by
`cm-charging-max`, already wired above), fast charge (stock `fast-charger@900` disabled) and charge watchdog (stock
`chg-wdt@80` disabled), PMIC ITERM register (covered in software by `cm-fullbatt-current`), `ovp-restart` (fixed
hardware hysteresis, no register).

## Driver changes needed

None for this DTS to build or probe. Optional: drivers for `btl,btl_ts`, `heartrate,bd1xxx` (stock config enables
`HEARTRATE_BD1820`, not in source), the camera sensors, AOD.

## Risks for a first boot and a first charge

* Display: no default panel; blank unless U-Boot passes `lcd_id`. Same first-enable-skipped and TE-pad risks as
  `devices/dm63/PANEL_414.md`. The three new streams are the stock bytes but were never run; a wrong variant gives a
  shifted picture.
* Touch: three stock candidates, two mapped; if the unit has the BetterLife chip there is no touch.
* Heart rate: `hrs3xxx` is mapped; if the unit has the BD1xxx chip there is no driver (both stock nodes use ap_gpio 55).
* First charge: attended, current limited supply. Charge limits depend on charger-manager running; check CV (4390 mV
  expected with calibration 0x20) and the OVP field. Every charge current is capped to 1050 mA (unknown adapter 1000 mA) by
  the adapter cap, the only thing between a zone request and the 1300 mA hardware maximum. Zone CV 4400 mV is above the
  battery maximum by design and is capped to 4395 mV. The OVP/CV interrupts are new and untested on hardware; a
  miswired `chg-ovi-gpios` shows as charging staying refused (`-EBUSY` in the kernel log) or as no reaction to a
  real over-voltage.
* Battery NTC: with `temp-support 1` the jeita temperature stops are live; the NTC table is the stock one (same as the
  DM63) and was not checked against this battery. A wrong table moves the zones.
* `regulator_late_cleanup()` can switch off rails stock keeps on; the same five are forced always-on as on the MT107.
* Reserved memory equals the MT107 / DM63 layout; a mismatch with U-Boot or the modem shows as a hang before the console.
* The rotary encoder driver stays inert (no node).
