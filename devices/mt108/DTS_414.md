# MT108 DTS for the 4.14 tree

File: `arch/arm64/boot/dts/sprd/sp9832e-1h10-mt108.dts`, panels `arch/arm64/boot/dts/sprd/lcd/lcd_st77916_mipi_{cto150,hsd185}.dtsi`.
Same method as the DM63 and DW100U files (`devices/dm63/DTS_414.md`, `devices/dw100u/DTS_414.md`, `devices/dm63/PANEL_414.md`,
`devices/SC2721_CHARGER_MAP.md`, `devices/SC2721_FGU_MAP.md`). Ground truth is the decompiled stock DT
(`devices/mt108/stock.dts` of the 4.4 tree, `SPEC.md` there). Compile only, nothing was run on a unit: `devices/merge_watch_414.sh $B`
then `make O=$B ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- dtbs` builds, no dtc warning for the new files (only host tool warnings).
Decompiled result checked against the stock DT: 14 reserved-memory regions identical, memory node identical, bootargs identical,
brightness table identical, init / sleep-in / sleep-out bytes of both panels identical.

Apart from the items below the file is the DM63 file: stock MT108 and DM63 DT differ only in the i2c layout, the USB cable method,
the pwm base, `bltc-rgb` enabled, a `sprd,v1-keypad` node, the battery and the panels (checked with a normalised diff).

Representability of 4395 mV in the 4.14 SC2721 model (`sc2721_cv_model()`): END_V 1 (4300 mV) plus round(95 / 7.5) = 13 code steps over
the efuse calibration, bit 0 of the code cleared. The default calibration 0x20 gives code 0x2d -> 0x2c, i.e. 4390 mV programmed
(request 4395). It stays END_V 1 for a calibration up to 0x32 (code <= 0x3f); from 0x33 the model falls back to END_V 2 with code
cal - 1, so the request stays representable for every calibration. The zone CV (4400 mV) is above the battery maximum (4395 mV),
the charger caps it to the battery maximum, as 4.4 does; every zone current is capped to the adapter current (450 mA, 420 mA unknown,
rounded down to the 50 mA step). The efuse calibration of the unit was not read.

## Display (ST77916)

SPEC.md only says ST77916 (U-Boot runs `lcd_st77916_init`), the stock DT has two ST77916 nodes and the `lcd_id` was never read, so both
are converted: `lcd_st77916_mipi_cto150` (lcd_id ID77916150, 1.50 inch, video burst, 340000 kbps, fps 50, 226 commands) and
`lcd_st77916_mipi_hsd185` (ID77916185, 1.85 inch, command mode, 334000 kbps, fps 60, 183 commands); both 360 x 360, one lane, bpp 18
(`rgb666_packed`), esd check off (stock `need-check-esd` 0, `esd-timeout` 1000). Conversion as in `PANEL_414.md`: `sprd,lcd-id`, `sprd,refresh-rate`
from `fps`, `sprd,phy-bit-clock` from the stock timing clock, byte strings copied as stock (data types checked to equal what the generic
write path derives from the length, `sprd,use-dcs-write` unset), reset sequences `<1 50> <0 50> <1 120>` (CTO) and `<1 20> <0 20> <1 50>`
(HSD) on gpio 50, power-off `<0 20>`. Neither stock node has an avdd step, so no `avdd-gpio` and none of the `sprd,avdd-*` properties.
There is no brightness command table (TFT): the brightness is the stock `sprd_backlight` (pwm-backlight on pwm index 0, 20000 ns, default 25,
256 entry table copied) as `sprd,backlight` of the panel. `sprd,width-mm` / `sprd,height-mm` are not in the stock node, the 4.14 defaults
(68 x 121 mm) stay. No `sprd,default-panel` (no variant is proven; without `lcd_id=` / `lcd_name=` the panel probe returns -ENODEV).

Why the display chain (dpu, iommu_dispc, dsi, dphy, pwms, pwm_backlight) is left disabled: the stock panels use bpp 18. The 4.4
`dpu_lite_r1p0.c` writes the DPI bus width from `panel->bpp` (`bus_width << 6`, 18 bit = 1) on both the dpi and the edpi path; the 4.14
`dpu_lite_r1p0.c` hard-codes 24 bit (`BIT(7)`) in `dpu_dpi_init()`, while the DSI host is set to the 18 bit packed coding from the panel
format. The generic panel driver cannot express this. The CO5300 panels of the other watches are 24 bit and are not affected.

Other open points of the panels: CTO 1.50 is video mode and the DPI clock is derived (stock has only the DSI bit clock and fps): 516 x 378 x
50 = 9.75 MHz; the 4.4 driver ran 128 MHz / 13 = 9.846 MHz; 4.14 `calc_dpi_clk_src()` needs an exact divisor of 96 / 128 / 153.6 MHz, so the
dtsi uses 9.6 MHz (96 MHz / 10, 49.2 fps). 4.14 warns when vsync + vback < 32 (stock 10). The command mode HSD 1.85 uses the same assumptions as the
CO5300 files (horizontal blanking 0 for the edpi selection, 128 MHz DPI clock, TE: the init stream turns TE on, no TE pinctrl). Mainline
pwm-backlight scales the duty by the last table entry (251), the stock driver by `brightness_max` 256 (2 percent at full brightness).
Panel AOD does not apply. The other 17 stock panel nodes are not converted.

## Needed driver changes (not done, no driver code touched)

1. `drivers/gpu/drm/sprd/dpu/dpu_lite_r1p0.c`: DPI bus width from the DSI format (18 bit for `rgb666_packed`), then enable the display chain.
2. Optional: `sprd,dsi-color-format` comment / dpu clock: calc of the DPI clock source for pixel clocks that are not an exact divisor.

## Risks for a first boot and a first charge

* Charge voltage: the battery maximum is 4395 mV, the charger programs 4390 mV with calibration 0x20 (the calibration was not read, other values
  shift it in 7.5 mV steps). Check CHGR_CTRL0 (0xec0) and the cell voltage on the first charges, attended, with a current limited supply.
* Adapter current 450 mA (420 mA unknown) with an SDP input limit of 500 mA in the second cell; jeita zone currents 100 / 500 / 700 mA are
  capped to 450 mA; no battery NTC, so jeita temperature zones and the cold / hot limits never act. No hardware charge timer, no ITERM /
  recharge programming, no OVP interrupt (see the DM63 note).
* Display stays dark in the 4.14 kernel until the DPU change; the serial console `ttyS1` and USB are the only outputs. The bootloader logo
  is still shown by U-Boot.
* The panel variant (and the touch IC: CST0xx at 0x38 or Betterlife at 0x2d, which has no driver) and the fitted accelerometer / heart rate part are
  unconfirmed; failed probes are expected for the absent ones.
* The USB path has no typec extcon (stock method "gpios"), peripheral only, no OTG VBUS regulator.
* Regulators, reserved memory and the first boot console are as the DM63 (`regulator_late_cleanup()` can switch off unlisted rails).
* The name `lcd_st77916_mipi_*` files may clash with the MT107 work if it uses the same panel (same names, merge by hand).
