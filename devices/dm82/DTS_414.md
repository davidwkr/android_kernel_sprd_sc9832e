# DM82 DTS for the 4.14 tree

Files: `arch/arm64/boot/dts/sprd/sp9832e-1h10-dm82.dts`, panel `arch/arm64/boot/dts/sprd/lcd/lcd_co5300_oled175_mipi.dtsi`.
Same method as the DM63 and MT108 files (`devices/dm63/DTS_414.md`, `devices/mt108/DTS_414.md`, `devices/dm63/PANEL_414.md`,
`devices/SC2721_CHARGER_MAP.md`, `devices/SC2721_FGU_MAP.md`). Ground truth is the decompiled stock DT (`devices/dm82/stock.dts`
and `SPEC.md` of the 4.4 tree). Compile only, nothing was run on a unit: `devices/merge_watch_414.sh $B` then
`make O=$B ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- dtbs` builds, no dtc warning for the new files (only host tool warnings).
Decompiled result checked: memory, bootargs, charger, battery, jeita table, panel properties as listed below.

The stock DM82 and MT108 DT differ in the i2c devices, the battery, the panels, `bltc-rgb` (disabled here) and the dispc register size;
memory, bootargs, the 14 reserved-memory regions, gpio-keys, rotary and USB (`"gpios"`, EIC 0) are the same, so the file starts from
the MT108 one (no logo reservation, same always-on regulators).

Representability in the 4.14 SC2721 model (`sc2721_cv_model()`, checked for every calibration 0..63 with the model's arithmetic):
* 4480 mV = END_V 1 plus code 24 over the calibration, bit 0 cleared: representable for calibration 0..39 (even calibration: exactly
  4480 mV, odd: 4472.5 mV); the default 0x20 gives code 56. For calibration 40..63 the stock arithmetic would wrap
  (4.4 then writes an arbitrary code); the 4.14 charger programs the highest representable CV not above the request
  instead and logs a warning.
* 4450 mV (zone CV): exact in the model for calibration 0..43 (even: exactly 4450 mV, odd 4442.5 mV), the same
  fallback above that.
So no calibration can push the CV above the request; a high calibration only charges a little lower.
  Known limit: with such a calibration the programmed CV can sit below `cm-fullbatt-voltage` (4450 mV), so
  charger-manager may never declare the battery full and keeps the cell held at that lower CV (safe direction:
  never above the request, current tapers at CV). The full and recharge thresholds are not derived from the
  programmed CV. The efuse
calibration of the unit was not read. The zone CV (4450) is below the battery maximum (4480), so the charger's CV cap does not act; every zone current
is capped to the adapter current (650 mA, unknown 630 mA rounded down to the 50 mA step, 600 mA).

## Display (CO5300 1.75 inch)

SPEC.md: U-Boot runs `co5300_mipi_init` and reads ID 0x33 0x11, so the controller is a CO5300; the stock DT has nine panel nodes and the
`lcd_id` the unit reports was never read ("most likely" ID5300175). Only `lcd5300175@5300175` is converted
(`lcd_co5300_oled175_mipi.dtsi`: `sprd,lcd-id` 0x5300175, `sprd,refresh-rate` 60 from fps, `sprd,phy-bit-clock` 460000, 468 x 466, bpp 24
= rgb888, one lane, command mode, esd check off with stock values, reset sequence `<1 20> <0 20> <1 50>`, off `<0 20>`, initial /
sleep-in / sleep-out bytes copied (112-byte init stream, 18 commands, types equal to the generic write path), single brightness command
`23 0a 00 02 51 00` (stock table is the identity "51 NN", script checked), default brightness 25). No existing `lcd/*.dtsi` is byte
identical (the 1.78 inch node has a similar vendor page prologue but another window and timing). `aod-in` / `aod-out` have no 4.14 port.
The other eight nodes (three 1.43 inch OLEDs with the same 468 x 466 geometry, ST7797, GC9B71, ST77916 CTO 1.50 (bpp 18), R63353, dummy) are not converted.

Board part as the DM63: avdd gpio 33 with `sprd,avdd-on-delay-ms` 20, `sprd,avdd-off-delay-ms` 20, `sprd,avdd-off-after-reset`, reset gpio 50,
`lcd-nosupply` fixed regulator. dpu, iommu_dispc, dsi and dphy are enabled (bpp 24, so the 24 bit DPI width of `dpu_lite_r1p0.c` is right);
gsp nodes keep their base state as on the DM63. No `sprd,default-panel`: SPEC.md does not state the reported lcd_id, so without
`lcd_id=` / `lcd_name=` the panel probe returns -ENODEV (blank, no crash). The only bpp 18 node is ST77916 CTO 1.50, which is not converted,
so the bpp 18 DPU limitation (MT108 notes) does not apply to this file; if the unit reports ID77916150 the display stays blank.

## Risks for a first boot and a first charge

* Charge voltage: battery maximum 4480 mV is high for a 1250 mAh cell; the charger programs 4480 mV (even calibration) or 4472.5 mV with
  calibration <= 39 and refuses it above (see above). Check CHGR_CTRL0 (0xec0) and the cell voltage on the first charges, attended, with a
  current limited supply. The `cv_override_mv` module parameter (4000..4400 mV) can lower it.
* Adapter current 650 mA (630 mA unknown) with an SDP limit of 500 mA in the second cell; jeita zone currents 100 / 500 / 700 mA are
  capped to the adapter current. The battery NTC is on (temp-support 1) and the table is the DM63 one, unverified for this cell. No
  hardware charge timer, no ITERM / recharge programming, no OVP interrupt (see the DM63 note).
* Touch: the fitted chip (CST0xx 0x38, Hynitron 0x5a or Betterlife 0x2d, which has no driver) is unknown; if it is the Hynitron, touch
  does nothing until `hynitron@5a` is enabled and `cst0xx_ts@38` disabled.
* Display: lcd_id unknown, no default panel (see above); TE pad not muxed as in the DM63; the first dsi enable is skipped on purpose.
* USB: stock method "gpios", peripheral only, no typec extcon, no OTG VBUS regulator.
* Regulators, reserved memory and the first boot console are as the DM63 (`regulator_late_cleanup()` can switch off unlisted rails).
